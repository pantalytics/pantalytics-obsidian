# Changelog

## Unreleased
- A new Excalidraw drawing that somebody else draws in before you have saved it keeps saving. Excalidraw used to say it "ran into an unknown problem" on every save, and nothing you drew after that reached the file. A new drawing has no text section until its first save, and without one Excalidraw lost track of the text the other person added. A drawing now gets that section as soon as it syncs. Opening a drawing while Obsidian starts also no longer fails with an empty scene. Tested with the Excalidraw plugin 2.29.
- Two people can draw in one Excalidraw drawing at the same time. While the drawing is open, each stroke shows on the other screen as it is drawn, and the other person's pointer shows with their name, the way it does on excalidraw.com. Until now a drawing synced as one block of text, and two people saving at once broke it: in almost every case the drawing no longer opened. A drawing is now kept per element, and when two people change the same element, Excalidraw's own rule picks which change stays. Drawings that were synced before move over the first time they are saved. Update Pantalytics on every device that opens drawings: an older version shows a moved drawing as empty, although nothing in it is lost. Tested with the Excalidraw plugin 2.29.
- Clicking into a table cell no longer puts the whole note into that cell. Live editing treated the cell as the note itself and filled it with everything in the note, line breaks turned into `<br>`. Obsidian then widened every row to match, and a short note grew to tens of thousands of characters.
- Two people in one note now see each other. Each caret shows with the person's name on it, and every key goes to the other screen as it is typed. Until now the live editor switched itself off the first time you clicked into a note. Nobody saw anybody's caret, typing only travelled when Obsidian saved the file, and two people typing at once got a conflict copy every few seconds.
- A key typed in the very moment a note connects goes in once. It used to land twice, or not at all.
- An edit made offline survives what happened in the cloud meanwhile. If somebody deleted the note, your edit brings it back instead of going down with it. If somebody renamed it, your file follows the new name and your edit is merged in. Before, both of these threw the offline edit away.
- A note you renamed while Obsidian was closed is a rename when you come back, not a delete and a new note. Its history stays with it, and an edit somebody made in the cloud meanwhile is kept.
- A note you deleted while offline stays deleted, unless somebody wrote in it since. Then it comes back with their words in it.
- Two people who make a note with the same name at the same moment get one note and one copy. Every other device used to make a copy of its own, named after a person who never wrote it.
- A device that joined a cloud vault empty now reports its real note count once the first sync is done. Before this, it reported the count from when Obsidian started, so the dashboard showed a freshly joined colleague at 1 note until they restarted Obsidian.
- You can see an AI write. When somebody's AI changes a note you have open, through the MCP, a caret with their name and *(AI)* shows up where it wrote, and what it wrote is highlighted in the caret's colour for a few seconds. The name is always visible, no hover needed.
- Linking compares both sides first and lets you choose when they differ. Before anything is written, the link scans this device and the cloud vault: the rows say what is different on each side, what has to come down and what has to go up. A device that already holds a copy of the cloud vault, after a reinstall or the move from Pantalytics Knap, just links, and only what is missing comes down. When the two really differ, linking used to stop. Now it asks. **Keep both** deletes nothing: both sides get everything, and a note that differs is kept in both versions. Its menu has the two other ways, **Use the cloud vault's notes** and **Use this device's notes**, which make one side the same as the other. Both of those ask first and say how many notes they delete.
- Pantalytics installs from Community plugins only. The steps for another device no longer mention BRAT and there is no repository to paste: search for Pantalytics, install it, sign in with the same account. Pantalytics Knap, the old plugin, can no longer sign in.
- The plugin is now **Pantalytics**, with the id `pantalytics`. It was *Pantalytics Knap* with the id `synced-vaults`, which named a product that is now part of your Pantalytics workspace and showed a word nobody recognised in the sign-in link and the plugin folder. Obsidian treats a new id as a new plugin, so this installs next to the old one. On first start it copies your sign-in, the vault link and what this device last synced from the old plugin, then turns the old plugin off so the two never sync one vault against each other. Nothing downloads again. Uninstall Pantalytics Knap afterwards. Every screen says Pantalytics now, and the repository is `pantalytics/pantalytics-obsidian`.
- Joining a cloud vault that already has settings takes them, and sends none of yours up. Settings travel per file, and a file the cloud vault had never heard of counted as new work from this device: somebody added to a colleague's vault sent their own plugins and snippets into it at link time, onto everybody, without being asked and without being told. The cloud vault's settings win the whole first pass now. Your theme, hotkeys and plugins on that vault become the ones up there, a notice says so and names the vault, and your notes are not touched. A cloud vault with no settings yet is still seeded from this device, and an ordinary restart is unchanged: a settings file you made here while the server was away is yours and still goes up. Which of the two a start is gets written down rather than remembered, so quitting Obsidian halfway through a first link comes back to the link rather than to a start that uploads.
- Linking refuses to merge two vaults that both hold notes. One of the two sides has to be empty, which is what both of the real journeys look like anyway: a cloud vault you made in the panel takes what is on this device, and a cloud vault somebody added you to comes down onto a device that has nothing yet. Notes on both sides is somebody linking the wrong pair, and until now it was quietly merged, which is the one act here with no undo: two notes at one path leave a conflict copy on every device, and two paths that look identical but are not leave two files. The link modal now stops on the counts it already had, names how much is on each side, and says what to do instead. Nothing is written and nothing is deleted, on either side.
- The plugin is called **Pantalytics Knap** in Obsidian's directory. Knap on its own is not a name the directory accepts: the entry was hidden on 2026-09-07 with *the name "Knap" is not allowed in the directory*, which is a rule about the listing rather than about the product. Nothing else moved. The identifier is still `synced-vaults`, so the plugin updates in place, and every word inside the plugin is still Knap, except the one Obsidian draws from the manifest: the settings tab now reads *Pantalytics Knap*, and so does the row in Community plugins.
- A way to Knap's own page, from the settings screen. Inviting somebody into a cloud vault and connecting an AI over MCP are the two things this side deliberately does not do, and until now nothing in Obsidian said where they are done: the address at the top of the screen is faint text nobody clicks. There is a **Knap dashboard** row under the vault now, with an Open button and an info button beside it, and the two sentences behind that button are all it says until somebody asks for them. Open lands on the linked vault's own page, the one with the member list on it, so it is one press from the name on the screen to the field that invites a colleague. It is there before you sign in too, because making a first cloud vault happens there as well.
- Obsidian's own settings travel with the cloud vault, if you turn them on. One switch in the Knap tab, off until you press it, and it carries the whole of `.obsidian`: your theme, your snippets, your hotkeys, your editor and graph settings, and your plugins with the settings you gave them. Two things stay on the device they are on. Which panes you have open is one, because that is a fact about a screen rather than about a vault, and it is also the only file in that folder that rewrites itself every few seconds. Knap's own folder is the other, because it holds your account and which cloud vault this one is linked to, and a copy of that arriving from somewhere else would sign you in as somebody else. Per file, the newer write wins, and there is no second copy left beside the first: a conflict file inside a folder Obsidian will not show you is litter rather than a rescue.
- Turning that switch on where the cloud vault already carries settings asks first, and names the vault, because it replaces the theme and hotkeys on this device with the ones up there. Your notes are not touched either way. The row itself is a name, an info button and the switch, and the button opens the two lists: what travels, and the short one that does not. A theme, a snippet or a hotkey applies straight away, measured against a real Obsidian rather than assumed. A plugin that arrives is on the disk and in the list, and starts the next time you open Obsidian, which is what Obsidian Sync does with community plugins too.
- A vault comes back up on its own after Obsidian starts without the server. Opening Obsidian on a train, or during a deploy, used to give up on the cloud vault after half a minute, say it would retry at the next sign-in, and then never retry: once the server was back the status read *Up to date* over a vault nothing was syncing, and the only way out was Try again or a restart. A start nobody is watching now waits for the server for as long as the link exists, the status says *Offline* while it does, and the first pass runs the moment the tree arrives. The link modal keeps its deadline, because a person is looking at it.
- The status says how far a restart has got. A restart over a vault that is already here opens every note, compares it against the cloud and closes it, which on a few thousand notes is minutes with nothing going up or down, and the strip said *Syncing* beside *2,505 notes* through all of it: no way to tell whether it was getting anywhere or how much was left. The head now counts the pass, *412 of 2,505*, climbing once a second, and a **Checked** line behind the fold keeps notes and attachments apart. The corner of the window draws the same count and a bar off it. It is not a new word, because what a person does under it is still wait; it is the number that was missing beside the word.
- The settings screen puts the sync status under the cloud vault it is about. It used to float above both rows as the first thing on the screen, which read as a third subject on a screen with two things on it; it is a fact about one cloud vault, so it now sits inside that row's block, sharing its border, and it appears only where there is a link. The Cloud vault row is the vault's name and nothing else, and the sentence about a delete travelling both ways moved to the modal that links, where somebody is choosing rather than reading a row they have read every week since.
- The fold behind that status is counts rather than sentences. **Uploading** and **Downloading** each get a line, named the way the word above them is and counting notes and attachments apart, and **Total** is the line under them: what the cloud vault holds, which is the one number here that can be held against what Knap's own page says about the same vault. The instruction under every word went with them, except Initializing's, which asks for something a person would not otherwise do: leave Obsidian open. The status head keeps the note count and drops the vault name, because the row a hairline above it spells that out.
- Linking a vault says what it is doing. Pressing a cloud vault in the picker used to close it and then show nothing until the whole first sync had finished, which on a vault of a few thousand notes is minutes: the promise the notice was waiting on did not settle until the job it was announcing had ended, so the only reading available was that the button had not worked. There is a modal now with eight steps in it, and the two near the end are what it is for: how many notes and attachments have to come down, and how many have to go up. It closes itself once the link is made, and the first sync runs on behind it.
- A vault in its first sync says **Initializing** rather than *Syncing*, with a sentence asking for the one thing that matters: leave Obsidian open until it finishes. Syncing means an ordinary catch-up, and its sentence says a person may close the laptop, which is true of a catch-up and wrong for a first pass over a vault that is not here yet. Whether a link has been through one is remembered, so quitting Obsidian halfway comes back to Initializing rather than to Syncing over a vault that is still half here.
- The corner of the window no longer reads *Up to date* for the moment between a link coming up and the reconciliation working out how much there is to do. The gauges behind that word are zero in that gap, and a status read in it said the vault was safe over notes that had not moved yet.
- The settings screen reads the vault once a second instead of once, when it opened. The bar is a reading and not an event: a socket comes up and goes down without telling anybody, so a screen drawn at the moment Settings opened said *Offline* over a link that connected a second later, and went on saying it until somebody closed Settings and came back. It is the same second the corner of the window already ticks at, off the same reading, and the fold survives a redraw because whether it is open is the person's decision rather than the screen's.
- **Try again** says it is trying. Behind that button a retry takes as long as the tree takes to sync, which is up to half a minute before it gives up, and until now the screen said nothing at all for that whole time and then swallowed the failure. Pressing it looked exactly like pressing a button that does nothing, which is how it was reported. The button now goes quiet and says *Trying...* while it goes, refuses a second press while the first is still out, and puts the reason on screen when it fails.
- Attachments travel. Images, PDFs and audio in a linked cloud vault now sync the way notes do: a file dropped into a note on one device turns up on the others, a delete takes it off all of them, and a rename moves it rather than re-uploading it. The transport for this has existed on both sides since the rebuild and nothing ever used it, because the binding returned early on anything that was not a `.md` and the vault adapter filtered attachments out of its file events before the binding could see them. What decides every direction is the file's SHA-256, recorded in the vault's tree beside the note map: same hash, nothing happens, which is also what keeps two devices from trading a photo back and forth forever.
- Two devices that wrote different bytes to the same attachment path keep both copies. The cloud copy takes the path and this device's copy is kept beside it, named for what happened, exactly as it works for a note. A binary has no merge and no text to rebuild it from, so this matters more there, not less.
- A file that is too large to sync says so, before the upload rather than after it. The cloud vault takes attachments up to 100 MB, and holds up to 10 GB of them in total; the plugin asks the server what those numbers are when it links rather than carrying its own copy, so a change on the server does not need a plugin release to take effect. A file over the ceiling stays on the device it is on and is never deleted, and a vault that has filled up says that instead, because leaving one file behind and clearing out a vault are different things to do about it.
- A bar in the corner of the window, under the count, while a vault is syncing. The count has been there since 1.12.6 and a count on its own is something a person has to read and then compare against the one they saw a minute ago, which is not what the corner of a window is for. It is the same two pixels the settings screen draws, off the same reading, so the mark in the corner and the Status row cannot disagree about one vault. It draws only against a real total, which is the sync queue on the device sending the notes and the cloud vault's file list on one that has just joined, so it never fills against a number that was guessed. It is absent rather than empty the rest of the time: an empty track beside a vault that is up to date reads as work nobody has started.
- The corner reads itself once a second instead of once every four. A count that lags a few seconds is a count; a bar that stands still while somebody is watching a first sync reads as stuck. It costs close to nothing, because the one expensive number behind it, the file list this device is still missing, is already cached inside the folder for a second and a half.

## 1.13.1
- An emoji is no longer cut in half by a sync. The text diff that reconciles a note against the relay works in UTF-16 code units, and it is free to put a boundary between the two halves of a surrogate pair. Two emoji that share a first half do exactly that: 🍎 and 🍊 differ only in their second half, so reordering two cards that carry them produced a diff of *keep the first half, delete one second half, insert the other* -- and the note came out holding lone surrogates, which is not text any more. It travels as an ordinary edit, so nothing downstream can tell it from something somebody typed, and it cannot be undone once it has been broadcast. Diff boundaries are now moved off the inside of a pair before anything is applied, and a whole code point is replaced as a whole. Vaults that use emoji in headings and folder names -- which is most of them -- were the ones exposed.
- A diff that does not land on the text it was computed for repairs itself before anyone sees it. The check is the invariant the function always had and never asserted: after applying, the note must equal the file it was reconciled against. If it does not, the smallest differing span is rewritten inside the same transaction, so no observer and no other device ever sees the bad intermediate. It costs one string comparison on a path that already holds both strings.
- A note that changed while the plugin was waiting for the relay is left alone instead of being reconciled against a stale copy of itself. The vault file is read first, then the plugin connects and waits for the relay to answer, and that wait is allowed to run for thirty seconds. Anything writing to the vault in that window -- the Kanban plugin and Excalidraw both write through `vault.modify`, outside the editor the plugin watches -- had its work reconciled away: the copy read half a minute earlier went into the document, and from there back over the file. The file is re-read immediately before reconciling now, and a file that moved is skipped and picked up by the next round with a fresh read. If the re-read itself fails, nothing is reconciled, on the same reasoning as every other step on this path: doing nothing is recoverable and writing the wrong thing is not.

## 1.13.0
- A local vault is linked to one cloud vault, and the link is a thing you can see (ADR-0066). Two local vaults on one account ended up holding each other's folder trees (#71), and the reason it stayed invisible is that "which cloud vault this local vault syncs" was never a fact anywhere -- it was read back off whichever share row happened to sit first in a settings array. An install that answered the sign-in screen more than once had several rows at the vault root, all of them reading as vault shares, and which one won was decided by array order. It is one record now, keyed by Obsidian's own id for this local vault, and reading it is the only way anything finds out which cloud vault is meant.
- Linking replaces rather than appends. Pointing a local vault at a different cloud vault takes the previous one off first, whether or not anything is mounted. The guard that was supposed to stop a second one only ever looked at what was mounted, so it did nothing in the one case that mattered: an update where the share had not come back, the screen offering the list again, and the answer landing beside the old row instead of on top of it.
- More than one cloud vault linked to one local vault is a fault, not a list to pick from. Nothing is mounted, the log says which vaults it cannot choose between, and the screen asks. A vault that is not syncing says so in the corner of the window within seconds, which is more than the silent wrong choice ever did.
- A link written by a different local vault is dropped rather than restored. The record has carried Obsidian's per-vault id since the memory existed and nothing read it, which is exactly the field that tells one local vault's answer from another's.
- The record is replaced whole rather than merged into. The caller that only knows an id passed the id alone and the name of whatever was linked before stayed sitting beside it, so an install could record one cloud vault's id under another cloud vault's name -- and did.
- A share on the account is no longer picked up because a local folder happens to share its name. A vault that is linked syncs whole, so nothing is auto-created beside it.
- The button on a row says **Link**, and there is an **Unlink** beside the vault it is linked to. Unlink deletes nothing: this device stops syncing, the notes stay on it, the cloud vault keeps everything in it, and linking again picks the two back up. Up to now the only way to stop was to delete the vault, which takes its documents with it. The list of vaults also says which one this local vault is already linked to, because changing a link and answering for the first time are different acts and the rows on their own cannot tell them apart.

## 1.12.6
- The plugin stops guessing at what else syncs your vault and hands you a checklist instead. The warning about Obsidian Sync fired on vaults that have never had Sync anywhere near them: it ships with Obsidian, so it reads as an enabled core plugin whether or not anybody has a subscription, has opened it, or has a single vault going through it. The cloud folder check had the same shape of problem from the other end, a guess off the folder's name that matched `Dropbox-notes` and missed a Dropbox folder mounted somewhere else, and on iOS it fired on the vault Obsidian makes for itself. A check that is wrong on the ordinary install teaches the one person who needs it that the warning means nothing. So the setup screen now says what to check, in three lines, and lets you check it: you can see your own Settings screen and your own folders, which is more than the plugin could ever work out.
- A vault that syncs whole stays that way across a restart. The record on disk never carried the one field that says so. The function that writes it built a settings object with the scope in it and then wrote a different one, so every share was stored as a folder share, and a vault share reloaded as a folder share at the path `""`, which is no folder in any vault. What kept this from being visible is that it was caught downstream: the memory of which cloud vault this device syncs (1.12.3) put the vault back on the way past, every start, and the screen only asked again when that fallback could not fire either. The scope is written now, and a stored share with no scope on it is read off its path, because the only share rooted at the vault itself is the vault share.
- The status can no longer say Up to date over a vault that has just arrived and is still empty. #40 was fixed for the device sending the notes and left open for the device receiving them: everything the status looked at is about work this device took on, and a phone that has just joined an existing cloud vault has taken none on. Nothing local to walk, a metadata document that catches up in seconds, an empty queue. All three agreed inside a minute over a vault with 2,567 notes still to come. There is a fourth fact now, and it is not about a queue at all: the notes the cloud vault lists against the files on this device. It is true from the first second, it stays true while a download runs, and it is what the count and the bar read from when there is nothing queued, so a phone fetching a vault says 267 of 2,567 rather than nothing at all.
- The setup screen ends with how to put Knap on your next device, including the exact line BRAT wants. BRAT's field asks for a Repository and every screen we had showed an address, so `https://github.com/pantalytics/knap-obsidian` went into a field that takes `pantalytics/knap-obsidian`. The line is a row of its own with a Copy button beside it, rather than a repository buried in the middle of a sentence, and the same string is on Knap's page.

## 1.12.4
- The cloud vault you picked survives a plugin update (#64). Every update through BRAT put the list of vaults back on the screen and waited to be told again, which is the one question this plugin promises to ask once. Which vault this device syncs was never written down as a fact of its own: it was read back out of the share record under `sharedFolders`, and that record is working machinery — it carries a guid, a path, a scope, a relay id and a bag of sync flags, and half a dozen code paths rewrite it while the vault runs. When it did not come back the way it was left, the screen saw no share covering the vault and did the only thing it knows how to do with that, which is ask. The answer now sits beside it in its own short record: the cloud vault's id, what it was called the day it was picked, which server it lives on, and Obsidian's own id for this local vault. Nothing derives it and nothing but a person changes it.
- A vault that is remembered but not mounted is put back on load, silently. It costs no request and asks nothing: mounting a share is local, and what goes back is exactly what pressing Sync mounts — the vault root, at vault scope, against the remembered id. It runs straight after the folders load and again when the settings screen opens, so nothing downstream ever sees a vault that syncs as a vault that has not been set up. An install that picked its vault in an earlier release fills the memory in from what is already mounted on the next load, so this does not start empty for anybody who is already syncing.
- Stopping a vault takes the memory with it. Wired to the one function that removes a share rather than to the buttons that call it, because a memory that outlived the share it remembers would put back the vault somebody just took off, which is the same fault the other way round.
- The pass that reconciles this device's shares with Knap can no longer turn a vault share into a folder share. It fired on a missing relay id, deleted the record, and rebuilt the share from the control plane's own path and the default scope — which for a vault share is a folder share at a path that does not exist on this device, so the next load looked for that folder, found nothing, and skipped it. A share already covering the whole vault is now left where it is and connected if it was not.

## 1.11.0
- The two halves of a vault have names now: the one Obsidian has open on this device is your **local vault**, and the one on Knap is your **cloud vault**. Everything about joining used to be said without a word for either, so the screen fell back to *Knap already has a vault called X* and left somebody to work out which of the two it meant. The entries below say which half they mean, everywhere both are in the same sentence.
- Starting a vault on Knap, or joining one, shows a checklist first: Obsidian Sync off, no other sync plugin running, and the vault folder not inside iCloud, OneDrive, Dropbox or Google Drive. The plugin already knew all three and only ever said the most serious one, as a warning; a person about to put their notes in the cloud gets the list with ticks against it instead, including the ones that came back fine. A second copy of Knap is the only thing that stops the button, because that one is two writers on one note. The rest say what it costs and let you carry on, since turning off a sync you pay for is a migration you schedule. *Check again* re-runs all three, so you can go and switch something off and come back.
- The list of vaults is drawn even when something else is syncing this vault. Up to now a blocking warning replaced the whole screen, so you were told no before you had seen what you were being told no about.
- Signing in shows the vaults on Knap your account reaches, and you pick the one this vault syncs with. Up to now the plugin matched on the name: a vault on Knap called exactly what your vault in Obsidian is called was joined, and anything else started a new one. That was wrong in both directions. A vault somebody shared with you is never called what your local vault is called, so there was no way to reach one at all; and a vault renamed in Obsidian, or a name typed by hand into a fresh vault on a phone, quietly started a second vault nobody asked for. The list is the account's own, owned vaults and vaults shared with you together, each row saying the name and the day it was added to Knap. Nothing syncs until you press one.
- An account with no vaults yet gets one button, which starts a vault named after this one in Obsidian. That is the only place the name is used now: it names the vault at the moment it is made, and after that the two are independent. Renaming either side changes nothing about which vault this device syncs with.
- Joining a vault that already has notes on this device asks first, and says what it is about to do in both directions: the vault on Knap downloads into this folder and everything already here uploads into it, so the two end up holding both. If that is not what you meant, the way out is Obsidian's own, which is to make an empty vault and join from there.
- One vault on Knap can be open in local vaults called different things, so the name it carries on Knap's page is no longer overwritten by whichever device connected last. A vault keeps the name it was given when it was started. There is no way to rename it yet.
- Sync vault no longer says two contradictory things at once. Pressing it put *Syncing all shares...* in the corner and *No shares to sync* directly under it, one second apart, over a vault that was syncing perfectly well. Two separate faults, and both are gone. The first notice was unconditional: it announced work before anything had counted whether there was any, so it could only agree with the second one by luck. When the control plane reports no OAuth provider the screen now says sign-in is unavailable instead of opening a form nobody has a credential for. Password login itself stays in `LoginManager`; what went is the UI for it.
- Auth (#14): one sign-in left a 30-day session behind per control-plane operation, not per sign-in. Every request re-derives its bearer token through `getValidToken()`, which refreshes — and so rotates the session — whenever `isTokenValid()` says no, and `isTokenValid()` subtracted a flat five minutes from expiry. A buffer only works while it is shorter than the token it guards: an access token that lives five minutes or less was expired from the instant it was minted, so the answer was no for its whole life and each operation bought another session. The buffer is now a quarter of the token's own lifetime, read from the JWT's `iat`/`exp` or, when those are absent, from the `expires_in` the control plane stated when it minted the token — `iat` is an optional claim, and scaling off it alone left every token without one on the flat five minutes.

And `refreshToken()` is now single-flight, so `restoreAuth()` and `reAuthForSensitiveAction()` join an in-flight refresh instead of sending a second POST carrying the same refresh token.
- Network: `customFetch` takes `replayable`, so a caller can overrule the method-based retry rule in either direction. Nothing in the plugin needs it today — the non-idempotent GET it was written for, the OAuth callback exchange, is gone now that the control plane exchanges the code itself — but the rule it overrules is a heuristic, and the next caller that knows better than its own HTTP verb can say so.
